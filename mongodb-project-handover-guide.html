MongoDB Atlas setup for the new developer

Use the same Atlas project only when the owner intends to share that project. For the safest handover, use a separate non-production database or dev cluster and a database user created specifically for the new developer. Atlas website access and database access are separate concepts.

Do not share an existing database password. Create a new database user, or rotate the existing user only if its credentials were exposed. Never grant a development tool access to production data just because the application can connect to it.

Create or accept Atlas access

Sign in to MongoDB Atlas. The owner should invite the developer to the intended organization/project if Atlas UI access is required. Do not send an Atlas account password.

Atlas website roles are documented in Atlas user roles. Project-level access is not the same as a database user. When a developer leaves the project or no longer needs access, remove their Atlas organization/project membership and their database user separately.

Select the correct organization and project

Choose the project that owns the development cluster. Confirm its name and environment with the owner before creating users or changing Network Access. ⚠️ Could not determine from the repository which Atlas organization/project is authoritative.

Create or select a development cluster

Use the existing development cluster only if its owner approves. Otherwise create the smallest transaction-capable dev deployment permitted by the project policy. The application relies on replica-set transactions; do not substitute an arbitrary standalone local server.

See Atlas free-tier cluster deployment and MongoDB transactions.

Create a database user

In Atlas, open Database Access and create a unique user such as <developer-id>_app_dev. Use a long random password stored in a password manager. Assign only readWrite on the non-production database <MONGODB_DATABASE>; do not use an Atlas Owner credential as the application credential.

Follow Configure database users. For this application, full local development, seeding, admin flows, and guarded integration writes need database writes. A read-only role cannot run those workflows.

Configure Network Access

In Network Access, add the developer's current public IP as an exact /32 entry, with a useful comment and an expiry if policy allows. Do not use 0.0.0.0/0 for normal development. Atlas applies the list to all clusters in the project.

See Configure IP access list entries.

Copy the driver URI

Open Database > Connect > Drivers, choose Node.js, and copy the SRV URI. The username and password occur inside the URI; they are not separate variables used by this repository.

mongodb+srv://<MONGODB_USERNAME>:<URL_ENCODED_MONGODB_PASSWORD>@<ATLAS_CLUSTER_HOST>/<MONGODB_DATABASE>?retryWrites=true&w=majority&appName=niro-platform

URL-encode the username and password when required. See connection string formats and the Node.js SCRAM authentication guide.

Configure the ignored root .env

From the repository root, copy the template and edit only the local file:

Copy-Item .env.example .env

Set MONGODB_URI, MONGODB_DB_NAME, and the local secrets described in the matrix below. Keep the database name unmistakably non-production, such as niro_dev or an owner-approved developer suffix containing dev or test when using public-test catalog mode.

Install and verify the connection

npm ci
npm run db:ping --workspace @niro/server

The ping should report status ok, the resolved database name, Atlas host, and ready state. It does not print the URI. Do not run cleanup-capable integration commands until the database name has been checked.

Bootstrap a separate local admin

Add these only to the ignored root .env for the one-time bootstrap. Use the developer's own email and a new password; do not reuse the owner's current bootstrap password.

ADMIN_BOOTSTRAP_EMAIL=<DEVELOPER_EMAIL>
ADMIN_BOOTSTRAP_PASSWORD=<ONE_TIME_BOOTSTRAP_PASSWORD>
ADMIN_BOOTSTRAP_ROLE=editor
npm run admin:bootstrap

The script uses $setOnInsert; if the email already exists, it does not reset that user's password. Use a unique email for a new account, then remove the bootstrap variables from the shell/file when finished.

Start and smoke-test the app

npm run dev

Open http://localhost:3000, http://localhost:3000/admin/login, http://localhost:4000/healthz, and http://localhost:4000/readyz. The root dev runner starts the server on port 4000 and gives Next.js CLIENT_PORT (default 3000).

Security checklist and audit

🔴 Critical

Credential-bearing ignored .env

The current root .env is present locally, ignored by Git, and contains set values for MONGODB_URI, ADMIN_BOOTSTRAP_PASSWORD, authentication secrets, and analytics HMAC. Do not include it in the handover. If it was copied, uploaded, committed, or shown to an untrusted person, rotate the Atlas database credential and all affected application secrets.

Owner action: create a new per-developer DB user, create fresh local application secrets, remove bootstrap values after one-time use, and verify the archive contains no .env.

🟠 Warning

Atlas access needs an ownership decision

⚠️ Could not determine from the repository whether the new developer should join the existing Atlas project or use a new one. Decide this outside Git. If joining, invite their own Atlas account with the least project role; do not share an Atlas login. Restrict the application database user to the dev database and, where possible, specific clusters.

🟠 Warning

Git history scope is incomplete

This checkout has one reachable commit and no tracked .env. That does not prove a remote repository, deleted branch, fork, tag, or earlier clone is clean. Before public sharing, audit the authoritative remote and all branches/tags. If a real secret appears in history, rotate it first, then use a documented history-rewrite process.

See GitHub's sensitive-data removal guidance.

🟠 Warning

Tracked generated/history artifacts

The repository includes generated/history/evidence material. The scan found no live credential-bearing URI in the tracked files inspected, but traces, screenshots, logs, and copied reports can capture sensitive data. Do not share tmp/, local build output, browser traces, database dumps, or unreviewed archives.

🟠 Warning

Example template omission

Add commented ADMIN_BOOTSTRAP_* placeholders to .env.example manually if the team wants a complete onboarding template. Keep the password line clearly marked as one-time and never place a real password there.

🟢 Safe

Existing ignore rules are appropriate

.gitignore ignores .env and .env.* while allowing .env.example. .dockerignore excludes environment files, dependencies, builds, caches, generated history, temporary files, and logs. Preserve this convention; do not add a broad rule that hides useful checked-in templates.

🟢 Safe

CI and Docker secret boundaries

CI references the protected GitHub p10-test secret rather than embedding an Atlas value. The client Dockerfile accepts public build values only; the server Dockerfile expects runtime injection. Never pass MongoDB/auth/analytics/metrics/revalidation secrets as Docker build arguments.

🟢 Safe

Test-only credential-like strings

Test fixtures include synthetic values such as a fake URI/password to verify redaction or production validation. They target example/non-routable hosts or are assertions; no live secret was found in the tracked scan. Keep them test-only.
