## 3. The Four Calculators (scoring truth, condensed)

### 3.1 Niro Comprehensive Wellness Score (CWS) — status: documented but REJECTED-pending (N1)

- 9 weighted domains: cardiovascular .25, metabolic .20, inflammatory .15, nutritional .10, liver .10, kidney .05, thyroid .05, hematological .05, hormonal .05 (Σ=1.0).
- ~40 parameters (38 lab biomarkers + systolic BP + derived eAG; deliverables consistently say "38"). Full point bands per parameter in PDF §3 / extraction §A / `niro-cws.config.json` v2 — including **negative protective points** (HDL ≥60 → −2), U-shaped bands (ferritin, bilirubin, TSH, MCV, WBC, platelets…), sex-split bands (ESR, ferritin, ALT, AST, GGT, creatinine, uric acid, hemoglobin, testosterone, estradiol), context bands (cortisol by draw time; estradiol by sex+menopausal status).
- Formulas: domain = Σpoints/maxPoints×100 → raw = weightedSum(domains) → **final = raw + Σ adjustments**. Adjustments: age 0–4 (<30/30s/40s/50s/≥60), BMI 0–4 (U: <18.5→4, 18.5–24.9→0 … ≥40→4), smoking 0–4 (never/former>5y/former<5y/current<10/current≥10), activity −2…+2 (≥150min→−2, 75–149→−1, <75→0, sedentary→+2). Gender: no separate points (baked into sex bands).
- Categories (lower-is-better): <10 Optimal · 10–20 Good · 21–30 Fair · 31–50 Suboptimal · >50 Poor. Interim continuous reading: min-inclusive edges **10/21/31/51** (C4 open at seams 20–21/30–31/50–51).
- eAG = 28.7×HbA1c−46.7 (ADA), **scored separately** from HbA1c (C6 resolved; yes, HbA1c effectively counts twice in Metabolic).
- Missing labs: `exclude-from-max` (shrink domain denominator) — interim default (C5), consistent with client's "partial risk score is normal".

### 3.3 Diabetes Risk (source-labeled ACTIVE, IDRS-based; application draft/publish-blocked)

Age ≤35→0 / 35–49→20 / 50+→30 (**Mandatory**; note: 35 double-assigned in source) · Waist M>90cm / F>80cm→10 (missing: impute 10 iff glycemic index ≥10) · Activity sedentary→30 / moderate→3 (source says 3, anomalous vs IDRS 20 — as-written) / regular→0 (missing default 3) · Family history none→0/one→10/both→20 (default 0) · **Glycemic index = max(HbA1c score, FBS score, PP score)** — "Take only maximum" verbatim. HbA1c <5.7→0/5.7–6.4→10/≥6.5→20; FBS <100→0/100–125→10/≥126→20; PP categorical (numeric cutoffs absent — N3). Categories <40 Low / 40–70 Moderate / >70 High **with escalation overrides:** glycemic 10 ⇒ ≥Moderate, 20 ⇒ High. Max attainable 110 vs declared scale 100 (source defect, flagged).

### 3.4 Heart Risk (source-labeled ACTIVE, "Modified Cardiovascular Risk Engine"; application draft/publish-blocked)

Modified-Framingham points: age 30–34→0 … 75+→12 (unisex table = men's coefficients — N6) · HDL ≥60→−2 … <35→2 · TC <160→0 … ≥280→5 · SBP untreated <120→−3…≥160→5 / treated <120→−1…≥160→7 / missing → age-imputed 0/1/2 · smoker→3 · glycemic status (derived from HbA1c/FBS) normal 0/borderline 1/high 4 · TG ≤150→0…>500→4. Then **24-row lookup** points→10-yr risk% (≤−2, −1, 0…20, 21+; deliverables 02/13 misstate it as "26-row") (≤−2→<1% … 13→10.0% … 21+→>30%; worked example 13→10% must reproduce). Then adjusted = base × S_lipid × M_young where S_lipid = 0.6×(LDL/100)+0.4×(TC/160), M_young = 2.5 (<30) / 1.8 (30–39) / 1 (≥40). Then **final = max(adjusted, floor penalty)** — isolated-high-cholesterol floors (apply when only lipids flagged): LDL <130→0 / 130–159→"12%–15%" (12 configured — N7) / 160–189→25% / ≥190→40%; TC ≥240→30%. **"Show both patient messaging in case of floor penalty rule"** (verbatim). Categories <10% Low / 10–19% Intermediate / >20% High (19–20% seam gap flagged). mmol/L→mg/dL "divide by 0.0259" (=38.61; library uses 38.67 — mismatch flagged).

## 4. Platform Architecture Decisions (from deliverables; adopted)

1. **Modular monolith** MERN; engine as pure workspace package (`packages/engine`), extractable for future NirogGyan integration. No microservices.
2. **Engine = pure function** `execute(config, inputs) → result`; no I/O/clock/randomness. Exact dependency-ordered semantics (including aggregate-dependent imputation) are locked in `packages/contracts/specs/engine-semantics.v1.md`; implementation will be TypeScript.
3. **Extended primitives** (required by real Niro calculators): `max()` group aggregation, lookup tables (`lookup()` w/ orBelow/orAbove + display strings), multiplicative/ternary formulas, imputation rules (fixed or by-band-on-another-param), floor rules + category overrides (`minCategory`).
4. **No eval:** conditions and formulas use the finite whitelist/AST/resource limits in the P0A semantic contract; unknown identifiers and alias collisions are rejected.
5. **Immutable versions:** lifecycle `draft → in-review → approved → published → retired` (with rejected review state); protected edits and rollback create new versions. Publish pointer/version/audit/review/revalidation changes are atomic.
6. **Server-authoritative scoring:** public config API strips bands/points/weights/formulas; trace admin-preview-only. Same validator + same engine used by builder preview and production.
7. **Band semantics:** default `[min,max)` with explicit overrides; array order never resolves overlap. Source gaps require `asWritten` + clarification IDs and produce no-score, not zero.
8. **Missing policies:** explicit per reachable optional scored parameter; no global default and no absent→false/zero coercion. Entirely missing domains require an explicit reviewed policy.
9. **Result hierarchy (fixed UX law):** RESULT → CATEGORY → WHY/KEY CONTRIBUTORS → DOMAIN DETAILS → BIOMARKER DETAILS → RECOMMENDATIONS.
10. **One React renderer for all calculators** via FieldRegistry (number/select/radio/boolean; derived never rendered) + FieldShell + ResultBlockRegistry (score-gauge, category, contributors, domain-breakdown, biomarker-details, recommendations); client `visibility.ts`/`validation.ts` mirror engine semantics; React Query + per-form useReducer; routes `/`, `/c/:slug`, `/results/:shareToken`, `/biomarkers[...]`, `/admin[...]`.
11. **Traceability first-class:** every medical value tagged `niro | external | needs-clarification` with `{org,title,url,accessed}` or `{ref}`; conflicts (19+ recorded) shown side-by-side per organization, never merged; biomarker draft→verified requires ≥1 source.
12. **Anonymous-first:** persistent pseudonymous `visitorId` is separate from short-lived `sessionId`; email capture is optional/separate; result shares use random expiring/revocable capability tokens and `noindex`; retention/lead linkage require product/legal approval before public APIs.

## 5. Database Design Decisions (MongoDB)

- **Core persistence:** 18 implemented collections: calculators + immutable calculator versions (including content/review/tests); versioned measurement revisions; assessments; exactly one v1 result per assessment; admin users/sessions and governance locks; audit logs; analytics events/daily/attribution claims/materialization locks/approved visitor state; leads; login attempts; durable job runs; and durable cache-invalidation events. Exact models and purposes follow Implementation-Plan §6.4 and P0A decisions.
- **Analytics additions (this build):** `analytics_events` (TTL), `analytics_attribution_claims` (TTL), `analytics_daily` (rollups), `analytics_materialization_locks`, `anonymous_visitors`, `job_runs`, `leads`, and `login_attempts` (TTL where specified). These reuse the application persistence boundary; they do not create a second analytics database.
- **Embed vs reference:** calculator versions embed every runtime config/content/measurement dependency. `parameters[].biomarkerKey` and revision IDs link to shared library identity for authoring/provenance, but old results never execute against a mutable current biomarker record.
- **Indexes:** representative implemented keys include unique `{calculatorId,version:-1}`, unique result `{assessmentId:1}`, result `{calculatorVersionId:1,createdAt:-1}`, event `{eventId:1}` plus time/calculator/HMAC-identity keys and absolute `expiresAt` TTL, daily `{day,timezone,scope,scopeKey,identityBasis,identityKeyVersion}` unique, audit `{entityType,entityId,createdAt:-1}`, and durable job/invalidation lease/retry keys. Implementation-Plan §6.6 and the Mongoose models are authoritative for the full list.
- **Mongoose:** the P1 model baseline is implemented. Config writes are always schema/semantic validated; optimistic concurrency applies to drafts. Publishing and assessment/result writes use transactions, with durable retry/outbox patterns where the downstream effect is asynchronous. Multi-instance caches require the P11 provider selection; P9 already exposes durable invalidation visibility.
- **Environments:** development and live integration use transaction-capable MongoDB Atlas; MongoDB server software is not required locally. Guarded synthetic suites use uniquely named, ownership-checked Atlas databases or scoped test records and clean only their owned data. The four P8 application drafts intentionally live in `niro_dev`. Production hosting/provider, access policy, backups, and alerts remain P11 decisions. The five `data/fixtures/config-samples/` files remain untouched draft fixtures, never published seeds.

## 7. Admin Requirements (incl. new dashboard scope)

- **Builder ("Admin Builder" in numbered deliverables = "Calculator Studio" in word/ docs — same thing):** wizard/workspace covers calculator logic plus the full structured content/SEO/citation/authorship/review contract. Roles include a distinct medical-reviewer permission. Required/golden test failures and protected medical-review failures block publishing; optional warnings remain warnings.
- **Dashboard (new requirement, this assignment):** panels — Overview (uniques, DAU/WAU/MAU, new-vs-returning, growth, live-now), Engagement (session duration, funnel per calculator w/ drop-off step, top pages, search terms, device/browser/referrer/UTM), Assessment intelligence (score distributions, category mix, omitted-parameter frequency, unit usage, computeMs), Leads (conversion, export), Security (admin login/logout, failed attempts, lockouts, 429s, per-admin activity), Ops (health, latency p95, error rate, job runs, cache hit rate). **No public user accounts exist** — "users" = anonymous sessionIds + leads; registered-member analytics deliberately out of scope unless Niro approves an optional accounts module later.
- **Analytics data flow:** client `sendBeacon` event batches → atomic TTL-bound HMAC session attribution claim → `analytics_events` (UA parsed server-side, no IP/raw-UA storage, no health data in events) → durable scheduled rollup with invocation and reporting-day leases → `analytics_daily` → dashboard APIs. Score/omission analytics aggregate from existing `assessments`+`results`.
- **Wishlist mappings (honest equivalents):** "new registrations" → new pseudonymous visitors within the approved retention window + leads; "most active users" → per-admin activity; "user-wise activity history" → per-admin audit history. Registered-member analytics remain out of scope.
- **FINAL AUTH MODEL (client decision 2026-08-20):** public users never log in or register — direct access to all calculators; the ONLY account type in the system is Admin (JWT + bcrypt + lockout + RBAC admin/editor). Do not add visitor accounts.
