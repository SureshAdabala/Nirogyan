2. CORE PRODUCT UNDERSTANDING
-----------------------------

Niro is intended to take health/lab information, interpret biomarkers, calculate a comprehensive wellness/risk score, and present the result in a simple, understandable way.

High-level flow:

User
  ↓
Health / Lab Data
  ↓
Biomarker Identification & Normalization
  ↓
Biomarker Interpretation
  ↓
Health Domain Scoring
  ↓
Weighted Wellness Calculation
  ↓
Demographic / Lifestyle Adjustments
  ↓
Final Wellness Score
  ↓
Wellness Category
  ↓
Explanation / Key Contributors
  ↓
Recommendations / Next Steps

Important distinction:
- Biomarker = what the measurement is.
- Biomarker result = the user's actual value.
- Interpretation = what that value means according to the configured rule.
- Wellness/Risk score = combined result from multiple parameters.
- Recommendation = user-facing action/explanation based on the calculated result.

4. COMPREHENSIVE WELLNESS SCORE (CWS)
--------------------------------------

The provided Niro risk-logic material defines a Comprehensive Wellness Score (CWS).

The score combines:
- Biomarker results
- Demographic factors
- Lifestyle factors
- Multiple health domains

The documented health domains and weights are:

1. Cardiovascular      — 25%
2. Metabolic           — 20%
3. Inflammatory        — 15%
4. Nutritional         — 10%
5. Liver               — 10%
6. Kidney              — 5%
7. Thyroid             — 5%
8. Hematological       — 5%
9. Hormonal            — 5%

Total = 100%.

6. DEMOGRAPHIC / LIFESTYLE ADJUSTMENTS
---------------------------------------

The documented CWS logic includes adjustments related to:
- Age
- BMI
- Smoking
- Physical activity

Some scoring is demographic/context dependent. For example, documented rules include gender-specific interpretation for certain biomarkers and context-specific handling for some hormonal measurements.

Therefore the implementation must support:
- Required demographic inputs
- Appropriate gender/sex-dependent rules where defined
- Units
- Context-dependent values where required
- Exact source-defined thresholds

7. SCORE CALCULATION MODEL
--------------------------

The documented model follows this structure:

Parameter values
  ↓
Parameter points
  ↓
Domain score

Domain Score:
Sum of parameter points / Maximum possible points × 100

Then apply domain weights:

Raw Wellness Score =
  Cardiovascular × 0.25
+ Metabolic × 0.20
+ Inflammatory × 0.15
+ Nutritional × 0.10
+ Liver × 0.10
+ Kidney × 0.05
+ Thyroid × 0.05
+ Hematological × 0.05
+ Hormonal × 0.05

Then:

Final Wellness Score =
Raw Wellness Score + Sum of documented adjustment points

The exact parameter points and thresholds must come from the source files.

8. DOCUMENTED WELLNESS CATEGORIES
---------------------------------

The documented score interpretation is:

< 10       → Optimal
10–20      → Good
21–30      → Fair
31–50      → Suboptimal
> 50       → Poor

These categories should be treated as the documented Niro CWS interpretation, not replaced by another model.

9. EXPECTED USER EXPERIENCE
---------------------------

The user should be able to:
- Provide/submit relevant health information
- Provide or have relevant biomarker values available
- Run the wellness assessment
- See the final wellness score
- See the wellness category
- Understand the major contributing health domains
- Drill into relevant biomarker/domain details
- Understand why the score was produced
- See appropriate recommendations/next steps supported by the source requirements

Preferred information hierarchy:

RESULT
  ↓
CATEGORY
  ↓
WHY / KEY CONTRIBUTORS
  ↓
DOMAIN DETAILS
  ↓
BIOMARKER DETAILS
  ↓
RECOMMENDATIONS

10. IMPORTANT TECHNICAL PRINCIPLE
---------------------------------

Keep the deterministic wellness/risk calculation separate from any AI explanation layer.

Preferred concept:

Structured User Data
  ↓
Deterministic Risk / Wellness Engine
  ↓
Score + Category + Contributors
  ↓
Explanation / Presentation Layer
  ↓
React UI

The calculation engine should be auditable, predictable, testable, and based on the source-defined rules.

Phase 5 — React UI/UX

- Build input screens.
- Build calculation/result experience.
- Build score/category presentation.
- Build domain and biomarker details.
- Build recommendations/next steps where supported.

Definition of Done:

Phase 6 — Integration
- Connect React with Express APIs.
- Connect MongoDB.
- Verify end-to-end data flow.
- Handle loading, empty, invalid, and missing-data states.

Definition of Done:
Full assessment works end-to-end.

Phase 7 — Testing & QA
- Unit-test every scoring rule.
- Test domain calculations.
- Test weighting.
- Test adjustments.
- Test category boundaries.
- Test demographic/context-specific rules.
- Test API validation.
- Test frontend flows.
- Run end-to-end QA.

Definition of Done:
Results match source-defined rules and critical flows pass.

Phase 8 — Final Polish & Release Readiness
- UI polish
- Accessibility/usability checks
- Error handling
- Performance checks
- Documentation
- Final QA

13. CRITICAL DEPENDENCIES
-------------------------

Phase 1 must be completed before implementation decisions.

Phase 2 depends on Phase 1.

Phase 3 depends on Phase 2.

Phase 4 depends on the rule/data model from Phase 2 and calculation engine design from Phase 3.

Phase 5 can begin UI exploration/design after Phase 1, but final integration depends on Phase 4.

Phase 6 starts only when the required frontend/backend contracts are stable.

Phase 7 starts after the integrated flow is available.

Phase 8 starts only after QA issues are resolved.

Parallel work is allowed only where dependencies are satisfied; do not start downstream implementation based on assumptions.
